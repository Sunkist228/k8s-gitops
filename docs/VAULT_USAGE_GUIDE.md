# Vault Usage Guide

## Purpose

This document is the primary operational guide for HashiCorp Vault in this repository.
It covers deployment model, bootstrap, day-2 operations, secret management flow with External Secrets Operator (ESO), and troubleshooting.

## Scope and Architecture

1. Vault is deployed by ArgoCD from Git.
2. Vault chart source is vendored in this repository:
   - `apps/vault/vault`
3. Runtime mode:
   - integrated storage (Raft)
   - UI enabled
   - single-node profile for current cluster (`ha.replicas: 1`)
4. Secrets for applications are not stored in Git.
5. Applications consume Kubernetes `Secret` objects generated by ESO from Vault KV v2.

## GitOps Sources of Truth

1. Vault app registration:
   - `bootstrap/apps/apps.yaml` (`Application` named `vault`)
2. Vault runtime values:
   - `apps/vault/vault/values-vault.yaml`
3. ESO app registration:
   - `bootstrap/apps/apps.yaml` (`Application` named `external-secrets`)
4. Vault provider configuration for ESO:
   - `apps/external-secrets-config/vault-clustersecretstore.yaml`

## Access Model

1. Internal Vault address in cluster:
   - `http://vault.vault.svc.cluster.local:8200`
2. UI service:
   - `vault-ui` in namespace `vault`
3. Recommended local access:
   - `kubectl -n vault port-forward svc/vault-ui 8200:8200`
   - open `http://localhost:8200`

Note:
- UI and API share the same Vault endpoint/port.
- Do not expose Vault publicly without TLS and authentication hardening.

## First Bootstrap (One-Time)

1. Wait until Vault pod is running:
   - `kubectl -n vault get pods`
2. Initialize Vault once:
   - `kubectl -n vault exec -it vault-0 -- vault operator init`
3. Store `Unseal Keys` and `Initial Root Token` in a secure external place.
4. Unseal Vault:
   - `kubectl -n vault exec -it vault-0 -- vault operator unseal`
   - repeat until `Sealed false` (threshold is usually `3/5`).
5. Verify state:
   - `kubectl -n vault exec vault-0 -- vault status`

Expected:
1. `Initialized true`
2. `Sealed false`

## CLI Usage Patterns

If local `vault` CLI is not installed, run commands inside pod:

1. Enter shell:
   - `kubectl -n vault exec -it vault-0 -- sh`
2. Set address and login:
   - `export VAULT_ADDR=http://127.0.0.1:8200`
   - `vault login <ROOT_TOKEN>`

## Secret Engine Configuration

This repository expects:
1. mount path: `secret/`
2. engine type: `kv`
3. version: `v2`

Check:
1. `vault secrets list -detailed`

If missing, create:
1. `vault secrets enable -path=secret -version=2 kv`

## Kubernetes Auth for External Secrets Operator

ESO uses Kubernetes auth role `external-secrets`.

### Step 1. Enable auth method

1. `vault auth enable kubernetes`

### Step 2. Configure auth backend

Run with valid cluster API values and token reviewer JWT:

1. `vault write auth/kubernetes/config kubernetes_host="https://<K8S_API_HOST>:443" kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt token_reviewer_jwt="<TOKEN_REVIEWER_JWT>"`

### Step 3. Create policy

Use policy with read access to required paths:

```hcl
path "secret/data/monitoring/*" {
  capabilities = ["read"]
}
path "secret/data/argocd/*" {
  capabilities = ["read"]
}
path "secret/data/n8n/*" {
  capabilities = ["read"]
}
path "secret/data/devops-tools/*" {
  capabilities = ["read"]
}
```

Apply:
1. `vault policy write external-secrets-read <policy-file.hcl>`

### Step 4. Bind Vault role to ESO service account

1. `vault write auth/kubernetes/role/external-secrets bound_service_account_names=external-secrets bound_service_account_namespaces=external-secrets policies=external-secrets-read ttl=1h`

## Writing Secrets (Correct KV v2 Syntax)

Important rules:
1. Use one `vault kv put` per secret path.
2. Use path without `/data/` in CLI commands.
3. Use exact key names expected by `ExternalSecret`.

### Required paths and keys

1. Monitoring Alertmanager:
   - `vault kv put secret/monitoring/alertmanager-telegram telegram-bot-token="<BOT_TOKEN>" telegram-chat-id="<CHAT_ID>"`
2. Monitoring Grafana:
   - `vault kv put secret/monitoring/grafana-admin admin-user="<ADMIN_USER>" admin-password="<ADMIN_PASSWORD>"`
3. ArgoCD notifications:
   - `vault kv put secret/argocd/notifications telegram-token="<BOT_TOKEN>" telegram-chat-id="<CHAT_ID>"`
4. n8n:
   - `vault kv put secret/n8n/auth N8N_BASIC_AUTH_PASSWORD="<N8N_PASSWORD>"`
5. Jenkins notify:
   - `vault kv put secret/devops-tools/jenkins-notify telegram-bot-token="<BOT_TOKEN>" telegram-chat-id="<CHAT_ID>" api-keys="<CSV_API_KEYS>"`
6. ingress-manager:
   - `vault kv put secret/devops-tools/ingress-manager API_KEY="<API_KEY>" DATABASE_URL="<DATABASE_URL>"`

### Verify a secret

1. `vault kv get secret/monitoring/alertmanager-telegram`
2. `vault kv get secret/n8n/auth`

## External Secrets Reconciliation Flow

1. `ClusterSecretStore` points ESO to Vault.
2. `ExternalSecret` resources reference Vault keys.
3. ESO creates/upserts Kubernetes `Secret` objects in target namespaces.

Check status:
1. `kubectl get clustersecretstore vault-backend -o yaml`
2. `kubectl get externalsecret -A`

Force immediate reconcile:
1. `kubectl -n <ns> annotate externalsecret <name> force-sync="$(date -Iseconds)" --overwrite`

PowerShell variant:
1. `$ts = Get-Date -Format s; kubectl -n <ns> annotate externalsecret <name> force-sync=$ts --overwrite`

## Workload Restart After Secret Changes

For env-based secrets, restart workloads to consume new values:

1. `kubectl -n monitoring rollout restart deployment kube-prometheus-stack-grafana`
2. `kubectl -n monitoring rollout restart statefulset alertmanager-kube-prometheus-stack-alertmanager`
3. `kubectl -n argocd rollout restart deployment argocd-notifications-controller`
4. `kubectl -n n8n rollout restart deployment n8n`
5. `kubectl -n devops-tools rollout restart deployment jenkins-notify`
6. `kubectl -n devops-tools rollout restart deployment ingress-manager-api`

## Common Errors and Fixes

### Error: `SecretSyncedError` + `Secret does not exist`

Cause:
1. Vault key path missing.
2. Key property missing in stored JSON/data.

Fix:
1. Write secret to expected path with exact key names.
2. Re-check with `vault kv get`.
3. Force ESO sync.

### Error: `no handler for route ... secret/data/...`

Cause:
1. KV v2 mount `secret/` does not exist.

Fix:
1. Enable KV v2 at `secret/`.

### Error: `no data provided` in UI REPL

Cause:
1. REPL parser issues with inline JSON format.

Fix:
1. Use Vault CLI (`vault kv put`) inside `vault-0` pod.

### Error: `403 preflight capability check returned 403`

Cause:
1. Token/policy lacks access to target path.

Fix:
1. Login with root/admin token.
2. Update policy for required capabilities.

### Pods pending with anti-affinity on single-node

Cause:
1. `ha.replicas > 1` with required anti-affinity and one node.

Fix:
1. Keep `ha.replicas: 1` for single-node profile.

## Backup and Restore (Raft Snapshot)

### Snapshot backup

1. `kubectl -n vault exec vault-0 -- vault operator raft snapshot save /tmp/vault.snap`
2. `kubectl -n vault cp vault/vault-0:/tmp/vault.snap ./vault.snap`

### Snapshot restore

Use only during controlled recovery window.

1. `kubectl -n vault cp ./vault.snap vault/vault-0:/tmp/vault.snap`
2. `kubectl -n vault exec vault-0 -- vault operator raft snapshot restore /tmp/vault.snap`

## Security Operations

1. Rotate exposed tokens immediately (Telegram bot tokens, API keys, DB credentials).
2. Update rotated values in Vault.
3. Force ESO reconcile and restart affected workloads.
4. Never commit secret values to Git (plaintext or base64).

## Operational Checklist

1. `vault` app is `Synced/Healthy`.
2. Vault status is `Initialized true`, `Sealed false`.
3. ESO pods are `Running`.
4. `ClusterSecretStore` is `Ready=True`.
5. All `ExternalSecret` objects are `Ready=True`.
6. Target Kubernetes `Secret` objects exist.
7. Dependent workloads are restarted and healthy.
